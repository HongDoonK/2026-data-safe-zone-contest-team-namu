# 별점은 누구의 책임을 묻는가

### 배달 지연이 가맹점 평판을 깎는 구조와 '공정 별점'

> 2026 데이터안심구역 경진대회 · 경북대 첨단정보통신융합산업기술원 트랙
> 주력 데이터: 공공배달앱 **대구로** 플랫폼 6종 (2022-01 ~ 2025-06, 42개월)
> 상세 설계 문서: `docs/topics/T5_platform_reputation.md`

---

## 1. 한 문장

주문·배달·리뷰를 하나로 이어 붙여, 가맹점 별점 중 **가맹점이 통제할 수 없는 몫**을 계산하고 그것을 걷어낸 **공정 별점**을 만든다.

---

## 2. 문제 정의

플랫폼 별점은 가맹점의 **음식과 서비스 품질**을 평가한다고 전제된다.

그러나 실제 별점에는 가맹점이 통제할 수 없는 요인이 섞여 들어간다.

- 배차 지연 — 라이더가 언제 배정되는가
- 피크 혼잡 — 그 시간대 그 동네의 배달 여건
- 배달 거리와 도로 사정

평점은 소상공인에게 **사실상의 신용점수**다. 노출 순위와 매출과 생존을 결정한다.
평판 시스템이 구조적으로 편향돼 있다면, 그것은 개별 가게의 불운이 아니라 **시장 실패이자 제도 설계의 문제**다.

> **왜 지금, 왜 이 데이터인가**
> 공공배달앱은 지자체가 운영·설계에 관여할 수 있는 **평점 산정식을 실제로 바꿀 수 있는 드문 대상**이다. 민간 플랫폼에는 제안만 할 수 있지만, 여기서는 적용할 수 있다.

---

## 3. 연구 질문

| # | 질문 | 답의 형태 |
|---|---|---|
| **Q1** | 별점 변동 중 **통제 가능 요인(조리)** 과 **통제 불가능 요인(배달)** 이 각각 얼마를 설명하는가 | 분산의 % |
| **Q2** | 통제 불가능 요인을 보정한 '공정 별점'은 원 별점과 얼마나 다르며 **가맹점 순위는 얼마나 바뀌는가** | 순위 변동 폭, 상위 20% 진출입 |
| **Q3** | 그 보정의 크기가 지역에 따라 다른가 — **특정 동네가 구조적 평판 페널티를 받는가** | 행정동 지도 |

이 셋의 **크기**가 이 연구의 가치다. "배달이 늦으면 별점이 낮다"는 직관적으로 당연하지만, **몇 %인지 · 순위가 얼마나 바뀌는지 · 어느 동네가 손해 보는지는 사전에 알 수 없다.**

## 4. 미개방데이터가 아니면 불가능한 이유

하나의 주문에 대해 **조리시간 · 배차시각 · 배달완료시각 · 별점이 모두 기록**되어야만 성립하는 질문이다.

| | 공개 크롤링으로 얻는 것 | 이 데이터로 얻는 것 |
|---|---|---|
| 별점 | ✅ | ✅ |
| 리뷰 텍스트 | ✅ | ❌ (텍스트 없음) |
| **배달이 실제로 몇 분 걸렸는가** | ❌ | ✅ **분 단위 실측** |
| **조리 대기 시간** | ❌ | ✅ |
| **약속 시간 대비 초과분** | ❌ | ✅ |

별점만으로는 낮은 평점의 원인이 **음식인지 배달인지 원리적으로 분해할 수 없다.**

### 5.2 데이터 구조에서 나온 제약 (설계를 바꾼 것들)

- **분 단위 소요시간은 배달 하나뿐** — 주문 측 시각(`ORDER_DT`, `COMP_TIME`, `SHOP_CONF_TIME`)은 전부 **시(hour) 단위**라 주문 내부 소요시간은 사용 불가. 조리 정보는 `COOK_WAIT`(10분 구간)로만 존재.
- **픽업 시각이 없다** — 배달 소요시간에서 "라이더가 가게에서 기다린 시간"(가맹점 책임 가능)과 "이동 시간"(가맹점 무책임)을 분리할 수 없다. → 공정 별점을 **구간으로 보고**하는 근거.
- **업종 컬럼이 없다** — 한식/치킨 등 카테고리 통제 불가. 가맹점 고정효과로 대체.
- **고객 위치가 없다** — 배달 거리를 근사할 방법이 없다. 지역 축은 전부 **가맹점 소재 행정동** 기준.

### 5.3 ⚠️ 리뷰 건수는 오기다 (정의서 검증 결과)

정의서 소개 시트의 리뷰 건수 8,767,828은 **주문 건수와 정확히 동일**하다. 파일 크기로 검증했다.

| 데이터 | 파일 크기 | 표기 건수 | 바이트/행 | 컬럼 구조와 정합? |
|---|---|---|---|---|
| 결제 | 611 MB | 7,881,627 | 81.3 B | ✅ |
| **리뷰** | **38.2 MB** | 8,767,828 | **4.6 B** | ❌ **불가능** |
| 배달 | 259 MB | 7,319,571 | 37.1 B | ✅ |
| 가맹점 | 0.8 MB | 22,087 | 38.0 B | ✅ |
| 고객 | 10.6 MB | 546,081 | 20.4 B | ✅ |
| 주문 | 529 MB | 8,767,828 | 63.3 B | ✅ |

리뷰 테이블은 **4개 컬럼뿐**(가맹점ID, 고객ID, 작성일 8자리, 별점 1자리)이라 1행 최소 길이가 15바이트다.
→ 38.2MB가 담을 수 있는 **행 수 상한은 약 267만**. 8,767,828은 어떤 인코딩으로도 불가능하다.

> **부수 효과** — 이 검증으로 대구로 데이터의 기간 논란(목록 시트 6개월 vs 소개 시트 42개월)도 해소됐다. 파일 크기가 42개월치와 정합한다.
> **첫 방문일 최우선 확인 항목**: 리뷰 파일 실제 행 수.

## 6. 분석 방법

### 6.1 전체 흐름

```
[Step 0] 데이터 품질 진단        ← 리뷰 실제 건수, 별점 분포, 매칭 가능성
   ↓
[Step 1] 집계 패널 구축 (보험)    ← 매칭 없이 즉시 가능. 결과 확보
   ↓
[Step 2] 개별 매칭 (상향 옵션)    ← 성공하면 주 사양으로 승격
   ↓
[Step 3] 식별 — 고정효과 + 위약검정
   ↓
[Step 4] 분산분해 → 공정 별점 → 순위 변동 → 행정동 지도
   ↓
[Step 5] 솔루션 — 평점 산정식 v0/v1/v2, 가맹점 진단 리포트
```

> **실행 순서 원칙 — 보험 우선**
> 매칭을 먼저 하지 않는다. **매칭이 전혀 필요 없는 집계 설계(2일)를 먼저 완성**해 결과를 확보한 뒤, 매칭은 병렬로 시도한다. 매칭이 실패해도 잃는 것이 없고, 성공하면 해상도가 올라간다.

### 6.2 Step 2 — 매칭: 이 주제 최대의 기술 과제

**문제**: 리뷰에 주문번호가 없다. 공통 키는 (고객ID, 가맹점ID)뿐이고 **시각 정밀도가 다르다.**

```
리뷰    REVIEW_TIME      YYYYMMDD      ← 일 단위
주문    ORDER_DT         YYYYMMDDHH    ← 시 단위
배달    DELI_ALLOC_TIME  YYYYMMDDHHmm  ← 분 단위
```

**매칭 규칙 4종을 병렬로 돌리고 결과를 브래킷한다.**

| 규칙 | 방식 | 편향의 방향 | 역할 |
|---|---|---|---|
| **M1** 동일자 유일 | 같은 날 주문이 정확히 1건일 때만 | 익일 작성 리뷰 소실 → **야간 주문이 체계적으로 빠진다** | 극보수 참조 |
| **M2** ±N일 최근접 | 리뷰일 기준 후방 N일 내 가장 가까운 주문 | 오배정 = 측정오차 → **계수가 0쪽으로 감쇠** (과대추정 안 함) | **주 사양** |
| **M3** 1:1 단조 배정 | 블록 내 최소비용 배정, 유일할 때만 채택 | **재주문 잦은 충성 고객 배제** → 표본 편중 | 상한 브래킷 |
| **M4** 확률적 가중 | 후보 k건 모두를 1/k 가중으로 포함 | 선택 편의 없음, 대신 감쇠 큼 | 하한 브래킷 |

> **핵심 논거** — M3는 *표본은 편중되지만 측정이 깨끗하고*, M4는 *표본은 온전하지만 측정이 흐리다*. **두 사양이 같은 부호·정합하는 크기를 내면, 서로 다른 두 실패 양식이 동시에 같은 방향으로 속여야만 결과가 가짜다.**

**정답이 없는데 매칭 품질을 어떻게 검증하는가**

| 방법 | 내용 |
|---|---|
| ⭐ **날짜 시프트 위약 매칭** | 리뷰 날짜를 +180일 밀거나 블록 내에서 무작위 치환한 뒤 **전체 파이프라인을 그대로 재실행**. 매칭률이 비슷하면 그 매칭은 우연이고, 계수가 0으로 돌아오지 않으면 매칭이 아닌 다른 것이 결과를 만들고 있다. 100회 반복 → 순열검정 |
| 시간 정합성 위반율 | 리뷰일 < 주문일, 배달완료 < 배차 등 모순 비율 = **오매칭률의 하한** |
| 모호도 회계 | "매칭률 87%" 같은 단일 숫자 금지. **후보 수 k의 분포를 그대로 공표** |
| 규칙 간 일치도 | 4개 규칙이 같은 주문을 지목한 비율 |
| 집계 정합성 역검증 | 매칭 표본 vs 전체 리뷰의 분포 비교 → 괴리 크면 역확률가중 |
| 명세곡선 | 규칙 × 창 × k상한 × 결과변수 전 조합의 계수를 한 장의 그림으로 |

### 6.3 Step 3 — 식별 전략

> ⚠️ **인과 주장을 하지 않는다.** 도구변수 접근(동시간대 인근 주문량)은 **폐기됐다** — 지역 혼잡이 배차뿐 아니라 **조리 지연을 통해서도** 별점에 직접 영향을 주므로 배제제약이 성립하지 않는다. 모든 결과는 **"조건부 연관"** 으로 표현한다.

**변수 구분**

| 구분 | 변수 |
|---|---|
| 결과 | `REVIEW_RANK` 1~5 |
| **배달 (통제 불가)** | 배달 소요시간 = 완료 − 배차 (분), 배달팁 |
| **조리 (통제 가능)** | 조리대기, **약속 대비 초과 조리시간** (= 조리대기 − 예상시간) |
| 통제 | 주문금액, 결제수단, 고객 성별·연령·가입경과, 착할매장 여부 |

**고정효과**

```
가맹점 (22,087) + 연월 (42) + 요일 (7) + 시간대 (6구간)
[견고성] 가맹점 × 분기,  행정동 × 연월
```

**추정량 3종 — 부수모수 문제를 정면으로 다룬다**

| | 방법 | 역할 |
|---|---|---|
| **S1** | 선형 2FE (고차원 고정효과 흡수) | **주 사양** — 계수 해석이 "별점 몇 점"으로 직관적 |
| **S2** | 조건부 로짓 (부정리뷰 이진화) | 부수모수 문제 없음 |
| **S3** | BUC 순서형 로짓 | 순서 구조 보존 + 부수모수 회피 |

**⭐ 포장주문 위약검정 — 이 설계의 핵심**

포장주문에는 배달 요인이 없다. 따라서 배달 계수가 0에 가까워야 한다.

단, 그대로는 성립하지 않는다 — **포장주문에는 배달 레코드 자체가 없어 배달 소요시간이 정의되지 않는다.** 추정대상을 맞춰야 한다.

```
1. 가맹점 × 연월-요일-시간대 셀의 leave-one-out 평균 배달 소요시간을 계산
   → 이 변수는 포장주문에도 정의된다 (그 가게가 그 시간대에 처한 배달 여건)

2. 두 표본에 같은 회귀를 돌린다
   배달주문 → 음(−) 계수 기대
   포장주문 → 0에 가까워야 함  ★ 위약
```

| 상황 | 대응 |
|---|---|
| 위약이 실패(포장에서도 음의 계수) | 결과를 폐기하지 않고 **"피크 혼잡의 총효과"로 재명명**. 배달·조리를 분리하지 않고 합산 보고. 주장은 약해지지만 정직하고 정책적으로는 여전히 유효 |
| 위약 표본이 작음 | **"유의하지 않다"를 근거로 쓰지 않는다.** 등가성 검정(TOST)으로 전환해 "효과가 δ보다 작다"를 적극 입증 |
| 포장 고객 선택 편의 | 위약이 요구하는 것은 "포장 고객 = 배달 고객"이 **아니다**. "포장 고객의 별점이 배달 여건과 무관하다"뿐이다. 수준 차이는 고정효과가 흡수하고, **기울기가 다를 때만** 문제. 그 위에 **포장·배달 둘 다 한 동일 고객 + 고객 고정효과**를 최강 사양으로 얹는다 |

**별점이 5점에 편중될 경우 — 사전 결정 규칙** (데이터를 보고 유리한 쪽을 고르지 않는다)

| 5점 비중 | 주 결과변수 |
|---|---|
| < 70% | 순서형 유지 (BUC) + 선형 병행 |
| 70 ~ 90% | 이진화 (4점 이하 = 부정) + 조건부 로짓 |
| ≥ 90% | 가맹점-월 부정리뷰율 집계 + Firth 벌점 로짓 |

> 편중이 심하다면 그 자체가 결과다 — **"현행 평점이 가맹점 간 품질을 거의 구분하지 못한다"** 는 발견이며, 평점 산정식 개선의 직접 근거가 된다.

### 6.4 Step 4 — 분산분해와 공정 별점

**분산분해: Shapley R²**

4개 요인군 — ① 가맹점 고유 ② 배달 ③ 조리 ④ 시간·지역 — 의 모든 부분집합 16개 회귀로 Shapley 값을 계산한다.

> 순차적 R² 증분을 쓰지 않는 이유: 결과가 투입 순서에 의존해 "왜 배달을 마지막에 넣었나"라는 질문에 답할 수 없다. Shapley는 순서 불변이라 이 공격을 원천 차단한다.

**두 기준으로 반드시 병기한다.**

| 기준 | 읽는 법 |
|---|---|
| 전체 분산 대비 | "별점 전체 변동에서 배달의 몫" |
| **가맹점 내 잔여분산 대비** | **"같은 가게 안에서 별점이 오르내리는 변동 중 배달의 몫"** ← 정책적으로 의미 있는 쪽 |

**공정 별점 — 무엇을 보정하고 무엇을 남기는가**

| 보정한다 (통제 불가) | 남긴다 (가맹점 책임) |
|---|---|
| 배달 소요시간 / 배차 여건 | 조리대기시간 |
| 시간대·지역의 배달 환경 | 약속 대비 초과 조리 |
| | 주문 취소 |
| | 음식·서비스에 귀속되는 잔차 |

**경계 사례**: 배달 소요시간의 일부는 가맹점 책임일 수 있다(음식이 늦게 준비돼 라이더가 대기). 픽업 시각이 없어 분리 불가 → **두 정의를 병기하고 구간으로 보고한다.**

- **보정 A (보수적)** — 가맹점·시간대의 공통 배달 여건만 제거. 개별 주문의 초과분은 남긴다
- **보정 B (적극적)** — 개별 주문의 배달 소요시간 전체를 보정

**⭐ 순위 변동은 3단으로 분리한다**

```
① 원 평균 별점 순위          (현행 플랫폼과 동일)
② 축소추정만 적용한 순위      ← 리뷰 수 보정 효과
③ 축소 + 배달여건 보정 순위   ← 이 연구의 주장

   ② → ③ 의 차이만이 "배달에 의한 평판 페널티"다.
   ① → ② 는 별개의 발견(평점 신뢰도 문제)으로 따로 보고한다.
```

섞어서 보고하면 "리뷰 수가 적어서 생긴 변동"을 "배달 때문"이라고 잘못 주장하게 된다.

**계층 베이지안 축소추정** — 가맹점별 리뷰 수 중앙값이 30 미만이면 적용. 주 산출은 경험적 베이즈(계산 즉시 가능, 한 줄 수식으로 설명 가능), 견고성은 층화 표본 500개 가맹점에 대한 완전 베이지안 순서형 모형.

## 7. 산출물

### 7.1 세 개의 숫자와 그림

| | 무엇을 보이나 | 그림 |
|---|---|---|
| **(a)** 분산의 몇 % | Shapley 몫 + 부트스트랩 구간 | **적층 막대 2개 병치** (전체분산 / 가맹점 내 잔여분산) + 배달시간 구간별 별점 곡선 — **배달주문 실선 vs 포장주문 점선** |
| **(b)** 순위 변동의 크기 | Spearman ρ, \|Δ백분위\| 중앙값·p90, **상위 20% 진입/이탈 가맹점 수** | **범프 차트** — 상위 20% 경계선을 가로선으로, 넘는 가맹점만 강조. 축소 단계는 회색으로 분리 |
| **(c)** 지역 체계성 | 행정동별 평판 페널티, Moran's I, LISA 핫스팟 | **대구 행정동 단계구분도** + 상하위 15개 행정동 신뢰구간 막대 |

> 왜 "상위 20%"인가 — 플랫폼 노출·추천 알고리즘이 실제로 참조하는 것은 연속 평점이 아니라 **임계값**이다. 몇 곳이 노출 구간을 넘나드는지가 현실 적용 가능성을 직접 말한다.

**③ 평점 산정식 v0 / v1 / v2 비교 시뮬레이터** ⭐ 핵심

| 버전 | 산정 방식 | 무엇을 고치나 |
|---|---|---|
| **v0** | 단순 산술평균 (현행) | — |
| **v1** | 축소추정 (리뷰 수 보정) | 리뷰가 적은 가맹점의 우연한 고·저평점 |

각 버전에서 산출: **상위 20% 노출 대상 명단의 변화**(진입 N곳 / 이탈 M곳), 행정동별 순이득·순손실 지도, 버전 간 순위 안정성, **운영 규칙 제안**(보정 계수 갱신 주기, 리뷰 수 하한, 신규 가맹점 처리).
